### D-05. Уведомления без передачи данных заявки в письмо

**Контекст:** Адрес из запроса можно подменить, а подробности ремонта в письме становятся доступны вне авторизованного приложения. Сбой SMTP не должен отменять сохранённые результаты диагностики или решение клиента.

**Решение:**

- Сервер определяет получателя по связи заявки с клиентом в БД. Адрес и текст письма из пользовательского запроса не используются. Перед каждой попыткой отправки проверяются владелец заявки и его текущий подтверждённый адрес; без подтверждённого адреса уведомление не отправляется.
- Письмо формируется по фиксированному шаблону: сообщение об обновлении заявки и ссылка на личный кабинет. В него не попадают жалоба, модель устройства, диагностика, фотографии, состав работ и стоимость. Ссылка не даёт доступа сама по себе: для просмотра нужны вход и проверка принадлежности заявки.
- Вместе с изменением заявки сервер в той же транзакции добавляет задание в таблицу уведомлений PostgreSQL. Задание содержит идентификатор заявки и тип события, без произвольного адреса или текста. Фоновый обработчик отправляет только зафиксированные задания. Ошибка SMTP меняет состояние задания, но не заявки; число повторов и интервал задаются в конфигурации. После исчерпания попыток задание отмечается как неотправленное.

**Обоснование:** Получателя выбирает сервер по сохранённой связи, а шаблон ограничивает раскрытие данных даже при пересылке письма. Отправка внутри транзакции заявки держала бы её открытой на время ответа SMTP и всё равно не позволяла бы отозвать уже доставленное письмо при откате БД. Задание в той же транзакции исключает отправку уведомления о несохранённом изменении.

**Связанные угрозы:** [T-09](https://github.com/exectly7/SecureDevelopment/blob/9c288503dd3413e6f858cfdc8a6dd4d0b9d94abb/docs/threat-model/threats/T-09.md).

**Связанные требования:** [SR-CLIENT-12](../security-requirements/client/SR-CLIENT-12.md), [SR-CLIENT-04](../security-requirements/client/SR-CLIENT-04.md) — источник связи с получателем.

**Будущая проверка:**

- **Условие:** Заявка принадлежит клиенту А с подтверждённой почтой; SMTP заменён тестовым приёмником.
- **Действие:** В запрос изменения заявки добавить адрес клиента Б и произвольный текст письма.
- **Ожидаемый результат:** Поля не влияют на отправку: письмо получает только А, тело соответствует шаблону. При неподтверждённом адресе письма нет. Переход по ссылке без входа не раскрывает сведения заявки.
- **Сбой отправки:** Отключить SMTP, сохранить результаты диагностики, затем восстановить SMTP. Изменение заявки остаётся сохранённым; повторяется только доставка задания. Согласие или отказ клиента не меняются.
- **Откат:** Вызвать ошибку транзакции после добавления задания. В БД нет ни изменения заявки, ни задания, тестовый SMTP не получает письмо.

**Ограничения и последствия:** Подтверждённая почта не исправляет ошибочную привязку заявки к клиенту; это ограничение остаётся и у D-03. Сам факт обращения в сервис может стать известен при пересылке письма. Если SMTP принял письмо, а обработчик не успел отметить доставку, повторная попытка может отправить его ещё раз. Это не должно повторять операцию над заявкой.
